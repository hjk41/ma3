## Executive Summary

On the fixed workload, aggregate client-observed `/search` average latency improved from **1213.7 ms** in the instrumented baseline to **17.3 ms** with all v2.1 optimizations enabled (**70.1x faster**).

Findings:

1. **Connection setup was the largest avoidable cost.** `/search` still did ~133 DB operations in baseline and pool-only, but pooling reduced server-side avg from ~1193 ms to ~87 ms.
2. **N+1 graph loading was the next largest cost.** Batch feedback/relation loading reduced `/search` DB operations from ~133.6 to ~8 and made `feedback_relation_fetch` ~2 ms.
3. **Runtime JSONB FTS became the remaining bottleneck after pooling/batching.** In `pool-batch`, `fts_content_search` averaged ~39 ms. Materialized `record_search_index` reduced FTS stages below 1 ms for v2 routes and made all normal `/search` requests ~10–11 ms avg.
4. **Full-scan fallback remains semantically questionable.** The synthetic no-hit request still returns top records due legacy full-scan fallback, but its latency is now bounded. A later ranking/UX design should decide whether no-hit queries should return no results instead of fallback matches.

## Recommendation

Enable the full v2.1 performance stack in the next production rollout:

```text
MA3_DB_POOL_ENABLED=1
MA3_DB_POOL_MIN_SIZE=1
MA3_DB_POOL_MAX_SIZE=8
MA3_DB_POOL_TIMEOUT_SECONDS=5
MA3_SEARCH_BATCH_GRAPH_ENABLED=1
MA3_SEARCH_INDEX_MODE=materialized
```

Keep rollback flags documented: set `MA3_SEARCH_INDEX_MODE=jsonb_runtime` to disable the materialized index path, set `MA3_SEARCH_BATCH_GRAPH_ENABLED=0` only if graph parity issues appear, and set `MA3_DB_POOL_ENABLED=0` only as an emergency benchmark/debug rollback because latency impact is large.
