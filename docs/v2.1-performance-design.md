# ma3 v2.1 Performance Improvement Design

Status: approved for implementation by designer on 2026-05-15  
Mode: implement in measurable slices; keep docs/tests aligned before each code change.  
Last updated: 2026-05-15

## 1. Context and Baseline

v2 production is running on the LTP-started instance behind `https://ma3.zhilicon.com`.
The immediate performance issue is search latency. Recent production metrics showed:

| Path | Count | Average latency |
| --- | ---: | ---: |
| `POST /search` | 31 | ~2068 ms |
| `POST /v2/search/explain` | 1 | ~204 ms |
| `POST /agent/ingest` | 10 | ~39 ms |

The slow path is therefore read/search, not write/ingest.

Current v2 design already names the high-level problem: v1-style agent loops are chatty, and search can load feedback and relations per candidate record. v2.1 narrows the next update to making the production search path measurable, then removing the largest avoidable costs without changing search semantics unless explicitly approved.

## 2. Goals

1. Reduce production `POST /search` average latency from ~2s to a target of **p50 < 500 ms** and **p95 < 1000 ms** for the current corpus size.
2. Bound database work per search so it scales with candidate batches rather than per-record N+1 queries.
3. Make each search stage observable enough to answer which stage caused latency regressions.
4. Preserve ranking behavior by default; performance work must not silently change result quality.
5. Keep v1-compatible `/search` working while making the v2 one-call retrieval path (`/v2/agent/context`) the preferred agent path after validation.

## 3. Non-goals

- No large ranking rewrite in v2.1.
- No semantic dedup redesign in this update.
- No raw query logging by default.
- No mandatory vector database introduction.
- No migration that risks data availability without a rollback path.

## 4. Current Bottleneck Hypotheses

### 4.1 Per-operation PostgreSQL connections

`server/app/storage/db.py` opens a new PostgreSQL connection every time `get_connection()` is called:

```python
psycopg.connect(settings.database_url, row_factory=dict_row)
```

Search performs multiple repository operations, so connection setup can be paid many times per request.

### 4.2 N+1 feedback and relation loading

`server/app/services/search_service.py` currently scores each candidate record by calling:

```python
feedback_repo.list_by_record(record.record_id)
relation_repo.list_by_record(record.record_id)
```

For `N` candidates this is `2N` additional repository calls, plus connection setup if each call opens a new PostgreSQL connection.

### 4.3 Runtime PostgreSQL FTS over JSONB

PostgreSQL FTS currently computes `to_tsvector(...)` from `payload_json` fields at query time. Tag search also expands JSONB tags at query time. This avoids schema changes but prevents efficient indexed search as the corpus grows.

### 4.4 Query embedding cost

For non-empty queries, search calls `embed_text(problem)`. With LTP production using `server/requirements-ltp.txt`, embeddings may be disabled; if enabled later, query encoding adds a fixed per-search cost and model cold-start risk.

### 4.5 Insufficient per-stage observability

Current metrics expose route-level count/sum and limited search count/sum. They do not tell whether a slow search spent time in FTS, DB connection setup, embedding, batch loads, N+1 loads, or scoring.

## 5. v2.1 Proposed Architecture

v2.1 should be delivered in four independently verifiable slices.

### Slice A — Search Stage Timing and Query-count Observability

Add an internal timing collector for search requests.

Each `/search`, `/v2/agent/context`, and `/v2/search/explain` request should record these stages when applicable:

- `fts_tag_search_ms`
- `fts_content_search_ms`
- `exact_tag_search_ms`
- `record_fetch_ms`
- `query_embedding_ms`
- `embedding_fetch_ms`
- `feedback_relation_fetch_ms`
- `scoring_ms`
- `total_ms`
- `candidate_count`
- `record_count_scored`
- `db_query_count`
- `db_connection_checkout_count`
- `full_scan`
- `ranking_config_version`

Expose these in two places:

1. Operation log event summary, without raw query text:
   - event type: `search_perf`
   - fields: `query_hash`, route, library id, stage timings, counts, result count, status.
2. Metrics:
   - `ma3_search_stage_duration_seconds_sum{route,stage}`
   - `ma3_search_stage_duration_seconds_count{route,stage}`
   - `ma3_db_queries_total{route,operation}`
   - `ma3_db_connection_checkouts_total{route}`

For `/v2/search/explain`, include stage timings in `explain.stages` so UI can display them.

Privacy rule: do not log raw `problem`, observations, constraints, or user free text. Existing `query_hash` and structured summaries are sufficient.

### Slice B — PostgreSQL Connection Pool

Introduce a process-local PostgreSQL connection pool.

Design:

- Use `psycopg_pool.ConnectionPool` when `MA3_DB_BACKEND=postgresql`.
- Keep SQLite behavior unchanged.
- Add environment variables:
  - `MA3_DB_POOL_ENABLED` default `1`; set `0` only for controlled benchmarks or emergency rollback
  - `MA3_DB_POOL_MIN_SIZE` default `1`
  - `MA3_DB_POOL_MAX_SIZE` default `8`
  - `MA3_DB_POOL_TIMEOUT_SECONDS` default `5`
- Initialize pool lazily on first PostgreSQL connection or during FastAPI startup.
- Close pool during FastAPI shutdown.
- Preserve the existing `DatabaseConnection` wrapper so repository code does not need broad changes.
- If pool initialization fails, fail fast at startup in production rather than silently falling back to unpooled connections.

Expected effect: reduce repeated connection setup cost across all API paths.

### Slice C — Batch Feedback and Relation Loading

Add repository batch APIs:

```python
FeedbackRepository.list_by_record_ids(record_ids: set[str]) -> dict[str, list[Feedback]]
RelationRepository.list_by_record_ids(record_ids: set[str]) -> dict[str, list[RecordRelation]]
```

Then update `search_records()` to:

1. Generate/fetch candidate records.
2. Filter out inactive/L0/critical records before relation loading when possible.
3. Batch-load feedback and relations once for the remaining record ids.
4. Score candidates using the batch maps.

This removes per-record feedback/relation repository calls.

The same batch APIs should be reused by `/v2/agent/context` if it still delegates to v1 search internally.

Benchmark/rollback flag:

- `MA3_SEARCH_BATCH_GRAPH_ENABLED=1` by default.
- Set `MA3_SEARCH_BATCH_GRAPH_ENABLED=0` only to measure legacy N+1 behavior or to roll back if result parity tests reveal a bug.

Expected effect: convert `O(N)` repository calls into `O(1)` batch calls for feedback and relations.

### Slice D — Indexed PostgreSQL Search Documents

Add production-oriented searchable fields while preserving JSON payload as the canonical record body.

Options:

1. **Materialized columns on `records`**
   - `search_text TEXT`
   - `tags_text TEXT`
   - `search_tsv TSVECTOR`
   - `tags_tsv TSVECTOR`
2. **Separate `record_search_index` table**
   - `record_id TEXT PRIMARY KEY`
   - `library_id TEXT`
   - `status TEXT`
   - `search_tsv TSVECTOR`
   - `tags_tsv TSVECTOR`
   - optional `updated_at`

Recommended for v2.1: use a separate `record_search_index` table. It avoids rewriting the core `records` table too much and gives a clear rebuild path.

Indexes:

```sql
CREATE INDEX idx_record_search_index_search_tsv ON record_search_index USING GIN(search_tsv);
CREATE INDEX idx_record_search_index_tags_tsv ON record_search_index USING GIN(tags_tsv);
CREATE INDEX idx_record_search_index_library_status ON record_search_index(library_id, status);
```

Update path:

- On record create/update/delete, upsert/delete index rows in the same logical operation.
- Add an idempotent backfill command or startup migration to rebuild missing rows.
- Add `/v2/doctor` checks for index row count and stale index count.

Rollback:

- Keep current JSONB FTS path behind a feature flag.
- New env var: `MA3_SEARCH_INDEX_MODE=jsonb_runtime|materialized`.
- Default first rollout can be `jsonb_runtime`; switch to `materialized` after validation.

Expected effect: reduce FTS candidate generation latency and make search scale better as records grow.

## 6. Client and API Behavior

### 6.1 `/search`

`POST /search` remains backward compatible.

Allowed changes:

- Faster execution.
- Added non-breaking response metadata only if clients tolerate it. Otherwise keep response unchanged.
- Operation logs and metrics include stage timings.

Not allowed without explicit designer approval:

- Changing default result ordering semantics.
- Changing visibility/library access semantics.
- Dropping legacy fields.

### 6.2 `/v2/agent/context`

After v2.1 validates correctness and latency, client skill can prefer `/v2/agent/context` for one-call retrieval.

This is a user-impacting behavior change and requires designer confirmation before client default changes.

### 6.3 `/v2/stats/search`

Extend stats to include recent hourly aggregates:

```json
{
  "window_hours": 48,
  "by_hour": [
    {
      "hour": "2026-05-15T02:00:00Z",
      "route": "/search",
      "count": 18,
      "avg_latency_ms": 2067.7,
      "p50_latency_ms": 1200.0,
      "p95_latency_ms": 4300.0,
      "max_latency_ms": 5200.0,
      "zero_results": 0,
      "full_scan": 0
    }
  ]
}
```

Implementation source can be `search_events` plus operation logs. If only aggregate metrics exist, the endpoint should clearly label values as cumulative and not pretend they are hourly.

## 7. Rollout Plan

### Phase 0 — Baseline

- Record current `/metrics` snapshot.
- Run a small repeatable search workload against current production or a staging clone.
- Capture count, avg, p50, p95, max, and top slow queries by query hash.

### Phase 1 — Observability only

- Add stage timing and query-count metrics.
- No search behavior change.
- Deploy to staging/LTP v2.1 candidate.
- Validate that no raw prompt/secrets appear in logs.

### Phase 2 — Pool and batch loading

- Enable PostgreSQL connection pool.
- Replace feedback/relation N+1 with batch loading.
- Keep ranking algorithm unchanged.
- Compare search result IDs/order against baseline queries.

### Phase 3 — Materialized search index behind flag

- Build `record_search_index` and backfill.
- Run dual-read validation: runtime JSONB FTS vs materialized FTS candidate sets.
- Enable `MA3_SEARCH_INDEX_MODE=materialized` only after candidate overlap and latency are acceptable.

### Phase 4 — Client preference decision

- If `/v2/agent/context` is stable and faster, request designer approval to make client `search`/warmup guidance prefer v2 context for agent retrieval.

## 8. Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| Connection pool leaks or exhaustion | FastAPI shutdown closes pool; tests simulate repeated requests; pool timeout metric/log event. |
| Batch loading changes relation/feedback scoring | Golden-result tests compare before/after ranking. |
| Materialized search index becomes stale | Same-operation upsert, startup/backfill repair, `/v2/doctor` index staleness check. |
| Query logs leak sensitive prompt content | Only store query hash, timing, counts, target/tags summaries; no raw problem text. |
| Performance improves but quality regresses | Replay/golden query set must compare top-k record IDs and judged useful results. |
| SQLite tests diverge from PostgreSQL behavior | Keep SQLite compatibility tests plus PostgreSQL integration/e2e test path. |

## 9. Required Tests

Every implementation slice must have corresponding tests before it is considered complete.

### 9.1 Unit Tests

- Stage timer records expected stage names and total duration.
- Metrics renderer exposes search stage metrics and DB query/connection metrics.
- `FeedbackRepository.list_by_record_ids` groups feedback by record id.
- `RelationRepository.list_by_record_ids` returns both incoming and outgoing relations grouped by relevant record id.
- `search_records()` no longer calls per-record `list_by_record` methods when candidates exist.
- PostgreSQL pool wrapper reuses the pool path while SQLite behavior remains unchanged.

### 9.2 API Tests

- `/metrics` includes:
  - `ma3_search_stage_duration_seconds_count`
  - `ma3_search_stage_duration_seconds_sum`
  - `ma3_db_queries_total`
  - `ma3_db_connection_checkouts_total`
- `/v2/search/explain` includes stage timings without raw prompt leakage.
- `/v2/stats/search` returns hourly aggregates or explicitly reports unavailable hourly data.

### 9.3 Integration Tests

- PostgreSQL-backed search returns the same top records before and after batch loading.
- PostgreSQL pool works for concurrent search requests.
- Materialized search index backfill creates one index row per active/searchable record.
- Runtime JSONB FTS and materialized FTS produce acceptable candidate overlap on a fixed fixture corpus.

### 9.4 Performance Tests

- Seed at least 300 records, 300 feedback rows, and 300 relations.
- Run representative query set with exact tags, broad text, zero-result, and case-related queries.
- Assert DB query count does not grow linearly with candidate count for feedback/relation loading.
- Assert p50/p95 latency target for staging hardware or document measured baseline if hardware is too variable.

### 9.5 Privacy/Logging Tests

- Raw `problem`, observations, constraints, API keys, tokens, and passwords do not appear in operation logs.
- Stage timing logs contain `query_hash` and counts but not raw query text.

## 10. Designer Decisions

Confirmed by the designer on 2026-05-15: do all proposed optimizations and measure the impact of each one on a new instance using a fixed request set.

Resolved decisions:

1. **Connection pool dependency**: add `psycopg_pool` via the `psycopg[pool]` extra.
2. **Search index storage**: use the separate `record_search_index` table.
3. **Index rollout default**: keep the feature flag and benchmark both `jsonb_runtime` and `materialized`; production can switch only after the report shows correctness and latency wins.
4. **Client default behavior**: do not change client default in this implementation. Measure `/search`, `/v2/search/explain`, and `/v2/agent/context`; propose client-default changes only in the report.
5. **Latency SLO**: use target `p50 < 500 ms`, `p95 < 1000 ms` for the current corpus size.
6. **Historical query replay**: store only privacy-preserving fixed benchmark requests in repo; production logs keep query hash and structured summaries, not raw user prompts.

## 10.1 Fixed Benchmark Request Set

The benchmark request set is a repo-owned JSONL file with deterministic synthetic/representative requests. It must not contain secrets or raw private user prompts. Each row includes a stable `name`, `route`, payload, expected minimum result count when known, and tags describing the case.

Initial request groups:

- Exact tag/product queries for ma3 deployment, LTP, MPI/RDMA, and client upgrade.
- Broad text queries that exercise content FTS.
- Low/no-result queries that exercise zero-result behavior without full scans.
- v2 explain/context requests that include target, task type, tags, and `include_explain`.

Benchmark dimensions:

- Route: `/search`, `/v2/search/explain`, `/v2/agent/context`.
- Mode:
  - `baseline-instrumented`: `MA3_DB_POOL_ENABLED=0`, `MA3_SEARCH_BATCH_GRAPH_ENABLED=0`, `MA3_SEARCH_INDEX_MODE=jsonb_runtime`
  - `pool-only`: `MA3_DB_POOL_ENABLED=1`, `MA3_SEARCH_BATCH_GRAPH_ENABLED=0`, `MA3_SEARCH_INDEX_MODE=jsonb_runtime`
  - `pool-batch`: `MA3_DB_POOL_ENABLED=1`, `MA3_SEARCH_BATCH_GRAPH_ENABLED=1`, `MA3_SEARCH_INDEX_MODE=jsonb_runtime`
  - `pool-batch-materialized`: `MA3_DB_POOL_ENABLED=1`, `MA3_SEARCH_BATCH_GRAPH_ENABLED=1`, `MA3_SEARCH_INDEX_MODE=materialized`
- Repetitions: default 5 warmups and 20 measured iterations per request.
- Metrics: count, avg, p50, p95, max, status distribution, result count, stage timings, and errors.

The benchmark runner writes JSON and Markdown reports under `reports/perf/` and must print a concise summary to stdout.

## 11. Acceptance Criteria

v2.1 performance improvement is complete only when:

- Design decisions above are resolved and reflected in this document.
- Tests in section 9 pass.
- Staging or LTP candidate shows lower `/search` latency than baseline.
- `/search` result quality is unchanged on golden queries unless an approved ranking change says otherwise.
- `/metrics`, `/v2/stats/search`, and operation logs make future latency analysis possible by hour and by stage.
- Deployment and rollback instructions are documented before production rollout.
